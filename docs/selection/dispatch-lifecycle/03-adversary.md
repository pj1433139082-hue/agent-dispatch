# 对抗性审查: 派单生命周期技术选型
（角色 adversary · 2026-10-22 · lead 代跑）

按"代价 × 概率"排序，≤7 条。

1. **假设「进程活着 = 任务在推进」** —— 代价高、概率高。
   反例实验：让 agent 卡在长思考/等外部响应，进程在、工具调用不增长；sweep 应显示 idle 增长。**判据只能看"最后一次工具调用时间"。**

2. **假设「产物时间 = 进度」** —— 代价高、概率高（今天已踩）。
   反例实验：只读探索阶段 4 分钟零产物。**这一条直接否掉"按产物判活"。**

3. **假设「到 deadline 就该杀」** —— 代价极高、概率中。
   反例：今天 6 个 agent 全在 deadline 前被我误杀。**deadline 只触发"看一眼"，不触发 kill。**

4. **假设「repair 重算可以覆盖 state」** —— 代价中、概率中。
   反例实验：造"state 有、disk 无"的条目，repair 若覆盖会删掉它。**要求：只做并集 + 冲突报告，绝不删条目。**

5. **假设「seat 计数反映真实名额」** —— 代价中、概率高。
   反例：DSH 的 8 人含 lead 与 inactive，dispatch 侧看不见宿主。**要求：occupied 由调用方显式给出，不许猜。**

6. **假设「env-hint 写了就等于环境就绪」** —— 代价中、概率中。
   反例：执行者可在缺依赖时仍宣称满足。**要求：回执附一条 env 检查命令的输出。**

7. **假设「单写者规则写进文档就会生效」** —— 代价高、概率高。
   反例：今天两个会话同时改 `cli.py`。**要求：除 AGENTS.md 外，加一条机器可查痕迹（技能仓 tickets 里先有票才允许改 src/）。**

## 结论三态：**需补证据**

先跑 #1/#2（判活口径）与 #4（repair 不删条），再签字；#3/#5 直接写进规格当约束；#6/#7 作为验收项。
